# WSL2 + ZFS: the distro dies during memory compaction (WSL kernel 6.6.123.2)

Investigated and fixed 2026-07-15. Environment at the time: Windows 11,
WSL 2.7.10.0, Ubuntu 24.04, custom-built WSL kernel
`6.6.123.2-microsoft-standard-WSL2+` (tag `linux-msft-wsl-6.6.123.2`, commit
`a07f9ea8a99139913acbcc1c160b132cb2a49c81`), OpenZFS `2.2.2-0ubuntu9.4`,
Codex CLI 0.144.4. Root and `/tmp` were ext4; the working directories and the
CLI's state directory were on ZFS datasets.

## Symptom

Windows Terminal closed the WSL session repeatedly with

```text
[process exited with code 1]
```

while Codex CLI was in use. `codex doctor` found nothing fatal, the CLI's log
ended mid-session without an error, and its last event (an HTTP 200 four
seconds earlier) was normal. The exit code was the *result* of the crash, not
its cause.

## Evidence

`journalctl --list-boots` showed several WSL restarts within an hour, and the
previous boot's kernel log carried the same BUG twice:

```text
kernel BUG at mm/migrate.c:662!
invalid opcode: 0000 [#1] PREEMPT SMP NOPTI
CPU: 4 PID: 203 Comm: mini_init
RIP: 0010:migrate_folio_extra+0x74/0x80
...
compact_zone
compact_node
sysctl_compaction_handler
proc_sys_write
vfs_write
ksys_write
...
Kernel panic - not syncing: Fatal exception
```

Line 662 of `mm/migrate.c` in that tree is

```c
BUG_ON(folio_test_writeback(src)); /* Writeback must be complete */
```

in `migrate_folio_extra()`. The stack shows WSL's `mini_init` writing to
`/proc/sys/vm/compact_memory` — explicit compaction — and the migration path
tripping the invariant. `zfs`/`spl` were loaded; the pools were `ONLINE` with
zero read/write/checksum errors, so this was not a storage fault.

## Cause

Linux 6.6's fallback for filesystems without a `migrate_folio` callback:

```c
static int fallback_migrate_folio(...)
{
	if (folio_test_dirty(src)) {
		switch (mode) {
		case MIGRATE_SYNC:
		case MIGRATE_SYNC_NO_COPY:
			break;
		default:
			return -EBUSY;
		}
		return writeout(mapping, src);
	}
	...
}
```

`writeout()` calls `mapping->a_ops->writepage()`. OpenZFS 2.2.2's Linux
address-space operations provide `writepage` but no `migrate_folio`, and ZFS
writeback completes asynchronously. So: a dirty ZFS folio → `->writepage()`
starts async writeback and drops the lock → the migration retries →
`migrate_folio_extra()` finds the source folio still under writeback →
`BUG_ON` → panic.

What is certain: the panic is the writeback invariant in the migration path.
What is strongly inferred (the mapping name is not in the trace): the folio
belonged to ZFS — everything else about the environment, timing and the
6.6/OpenZFS-2.2 interaction fits, and upstream removed exactly this call.

## Fix applied: semantic backport of upstream `7ee3647243e5`

Upstream Linux commit
[`7ee3647243e5c4a9d74d4c7ec621eac75c6d37ea`](https://github.com/torvalds/linux/commit/7ee3647243e5c4a9d74d4c7ec621eac75c6d37ea)
("migrate: Remove call to ->writepage") stops migration from initiating
filesystem writeback. It does not apply verbatim to 6.6 (that tree still has
`MIGRATE_SYNC_NO_COPY` and the older helper signatures), so the backport keeps
the meaning: delete the static `writeout()` helper and replace the dirty-folio
switch with

```c
if (folio_test_dirty(src))
	return -EBUSY;
```

Patch: [`../patches/0001-migrate-remove-writepage-from-fallback-wsl-6.6.123.2.patch`](../patches/0001-migrate-remove-writepage-from-fallback-wsl-6.6.123.2.patch)
(`git apply --check` passes on `linux-msft-wsl-6.6.123.2`).

Procedure that was followed:

1. Branch the kernel tree, apply the patch, build (`make -j$(nproc) KCONFIG_CONFIG=Microsoft/config-wsl`); the release became `6.6.123.2-microsoft-standard-WSL2-migratefix+`.
2. Rebuild and install the OpenZFS DKMS modules for the new release and confirm `zfs.ko`/`spl.ko` vermagic equals the release string. (Caution learned the hard way: the still-running unpatched kernel panicked again *during* the DKMS install and left zero-byte `.ko` files despite DKMS reporting success. Re-run the install and `sync` immediately; verify file sizes and `modinfo` before trusting it.)
3. Copy `bzImage` to the Windows side under a **new** name, keep the previous image and a backup of `.wslconfig` for rollback, point `kernel=` at the new image, `wsl --shutdown`.
4. After reboot: `uname -r`, `modprobe zfs`, `zfs version`, `zpool status -x`, and a kernel log free of `migrate_folio_extra` / `kernel BUG` / `Kernel panic`.

Verified result: the patched kernel booted, both pools imported `ONLINE` with
no errors, Docker and `systemd-modules-load` were active, and the panic did not
recur under the same workload.

## What did not help

- `autoMemoryReclaim=disabled` — it was already disabled; the compaction came from `mini_init`'s explicit sysctl write, not from reclaim.
- `vm.compaction_proactiveness=0` — suppresses proactive compaction only; an explicit write to `compact_memory` still runs.
- Softening the `BUG_ON` — hides the panic and leaves the dangerous `->writepage()`-during-migration path in place.
- Moving the CLI's state and working directories to ext4 — a mitigation, not a fix; any other ZFS writer can still hit the same path.

Do not try to reproduce with `echo 1 > /proc/sys/vm/compact_memory` on a
machine with live pools: on the unpatched kernel it panics the VM immediately
and exports the pools uncleanly.

## Where this stands now (2026-09)

The environment moved to Ubuntu 26.04, OpenZFS 2.4.1 and WSL kernel
6.18.35.2. That tree already contains the upstream change:

```c
static int fallback_migrate_folio(struct address_space *mapping,
		struct folio *dst, struct folio *src, enum migrate_mode mode)
{
	WARN_ONCE(mapping->a_ops->writepages,
			"%ps does not implement migrate_folio\n",
			mapping->a_ops);
	if (folio_test_dirty(src))
		return -EBUSY;
```

so the patch is not applied there; the post-build regression check is to read
that function and confirm the `-EBUSY` return. The build itself is stock
(config delta is toolchain-only) and is recorded at
[mkjung/WSL2-Linux-Kernel @ `mksols/linux-msft-wsl-6.18.35.2-zfs-build`](https://github.com/mkjung/WSL2-Linux-Kernel/tree/mksols/linux-msft-wsl-6.18.35.2-zfs-build/mksols/6.18.35.2).

## A side finding: modprobe inline comments

`/etc/modprobe.d/zfs.conf` had inline comments:

```conf
options zfs zfs_arc_max=2147483648    # 2 GiB
```

modprobe passes the trailing tokens as module parameters, so boot logged
`zfs: unknown parameter '#'`, `'2'`, `'GiB'`. Harmless for the ARC values
themselves, but noisy; see [`../examples/zfs-modprobe.conf`](../examples/zfs-modprobe.conf)
for the corrected form.
